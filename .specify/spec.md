## 1. Glossary

| Term | Meaning |
|---|---|
| **DRS** | Driver Route Sheet — one driver's set of consignments for a day, identified by `drsNo`. Existing concept, used throughout `app/db/firestore.py`, `app/db/bigquery.py`. |
| **Consignment** | A single parcel/delivery record. Existing Firestore `consignments` collection, `consignmentId` primary key. |
| **Geohash** (locality/building/exact) | A string encoding of lat/lon into a base-32 string where shared prefixes mean physical proximity. Already used at three precisions: `geohash_locality_loc` (5 chars), `geohash_building_loc` (6 chars), `geohash_exact_loc` (8 chars) — see `app/config.py:19-20`, generated by `pgh.encode()` in `app/services/save.py`. |
| **`geohash_group_id`** | Existing BQ/Firestore field, format `<drsNo>_<geohash_locality_loc>`. Sentinel value `'UNASSIGNED'` means "not yet routed" — this is the default BigQuery inserts today (`app/db/bigquery.py:111`), *before* this spec adds any new meaning to it. |
| **`geocode_status` / `geocode_error`** | Existing BQ/Firestore columns (`app/services/save.py:59,71`). Today only two values exist: `"success"` / `"failed"`. This spec adds new *values*, not new columns (see §5.1). |
| **TSP solver** | The route-ordering algorithm. Existing: `app/services/tsp.py`, OR-Tools open-path solver over a haversine distance matrix. |
| **Master waypoint** *(new)* | A small, curated, high-confidence address → coordinate anchor (e.g. a large apartment complex's verified gate location). Checked *before* the geocode cache/API, at $0 marginal cost. Promoted only through repeated confirmation (§5.3), never guessed. |
| **HILT** *(new — coined in this document)* | **H**uman-**I**n-**t**he-**L**oop-**T**riage: the status + queue a consignment enters when its geocode result cannot be auto-trusted (ambiguous, not found, or a solitary outlier). Nothing routes to a driver from HILT state until a human resolves it. |
| **Solitary-outlier trap** *(new)* | A pre-DRS-creation check: if one stop sits far outside the geographic cluster of the rest of the route (e.g. ~10km away), the system refuses to finalize the DRS until the point is fixed or explicitly overridden, instead of silently routing to it. |
| **EOD (End of Day) debrief** | An **existing process in the external mobile driver app** (not part of this repo). At day's end it (a) marks undelivered consignments for next-day retry, and (b) asks drivers a confirmation question when actual delivery location deviated >500m from the planned waypoint. |
| **>500m confirmance question** | The specific EOD question: "was this waypoint accurate?" with a reason code (§5.4) when the answer is no. |
| **Anchor & Hitchhiker routing** | A routing strategy name that exists **only** in this conversation and a prior Gemini chat — not documented anywhere else, not specified in this file. Explicitly out of scope (§7) until it has its own spec. |
| **BQML** | BigQuery ML — lets you define and call ML models using SQL, from inside BigQuery. |
| **Remote model (BQML)** | A BQML model definition that proxies calls to an externally-hosted model (e.g. a Vertex AI embedding model) rather than training one in BigQuery. |
| **`text-embedding-005`** | A Google-hosted text embedding model, called here via a BQML remote model. |
| **`VECTOR_SEARCH` / `ML.DISTANCE`** | BigQuery SQL functions for nearest-neighbor / cosine-distance search over embedding columns. |
| **Haversine distance** | Great-circle distance formula. Already implemented: `app/services/tsp.py:17`, `haversine_distance()`. Reused, not reimplemented, by every new distance check in this spec. |
| **Feature flag** | A config value that turns a piece of behavior on/off (or scopes it to a subset of traffic) without a code deploy. Used here (§5.6) so every new requirement in this spec can ship disabled and be enabled deliberately. |
| **Canary (rollout)** | Enabling new behavior for a small, deliberately chosen subset first (here: specific DRSs/depots, or a percentage via a deterministic hash of `drsNo`) before enabling it for everyone, to catch problems while blast radius is still small. |
| **Dark launch / default-OFF** | Merging new code to production while its feature flag is off, so it exists in the deployed service but has no live effect until deliberately enabled. |
| **Config version** | An incrementing identifier on a config/flag document, stamped onto any record that resulted from a flagged decision, so "what threshold was active when this happened" is answerable later without guessing from current config. |

## 3. Problem

Verified against the current code, not against the original (Gemini-authored) proposal text:

1. **Geocoding has no ambiguity handling.** `app/services/geocoding.py:115` takes `places[0]` unconditionally, regardless of how many candidates came back or whether the top one is inside the expected delivery area. `geocode_status` today is binary — there is no state for "resolved, but not trustworthy."
2. **Nothing stops one bad point from wrecking a route.** Clustering (`geohash_group_id`) groups stops for sequencing, but nothing checks whether a stop is a *distance outlier* before a DRS is finalized — see the solitary-outlier trap (§5.2). A single bad geocode is silently routed today.
3. **EOD driver-debrief data never reaches this system.** The mobile app's EOD process already asks drivers the >500m confirmance question and already handles undelivered rollover, but none of that data flows into Route-Optimization, so it can't correct future routing or train anything.
4. **No resolution path exists once ambiguity is detected.** There's no defined queue or taxonomy (HILT) for a human to resolve an ambiguous/unfound address, and no promotion path for a corrected point to become trusted for future use.

---

## 4. Solution direction

- **Geocoding ambiguity → HILT** (§5.1). Classify every geocode result into: known-good (master-waypoint or verified-cache hit), confident single match, `ZERO_RESULTS`, or multiple in-bounds candidates. The latter two enter HILT, tagged with *why*.
- **Solitary-outlier gate** (§5.2). Before DRS creation, check each stop's distance from its cluster (reusing `haversine_distance`). An outlier blocks DRS creation and routes to HILT instead of silently entering the TSP solve.
- **Master-waypoint tier** (§5.3). A curated, promoted-by-confirmation address set, checked first, ahead of `geocache.py` and the external API.
- **EOD ingestion contract** (§5.4). A defined data contract + new endpoint so the *existing* mobile app's EOD debrief (undelivered rollover, >500m confirmation + reason code) can feed this repo. The confirmation is the master-waypoint promotion signal — used **proactively**, before the next day's routing, not just for after-the-fact reporting.
- **BQML/vector-search embeddings** (§5.5), always pincode/geohash-6-bounded, used both as a secondary fuzzy matcher and trained/evaluated against EOD-confirmed corrections as ground truth.

## 5. In scope right now

### 5.1 Geocoding ambiguity → HILT

**Taxonomy** (the "standard way to bifurcate" requested):

| Bucket | Condition | Resolution |
|---|---|---|
| Known-good | Master-waypoint or `geocache.py` verified hit | Auto-resolve, no API call |
| Confident single match | Places API returns exactly one in-bounds candidate | Auto-resolve |
| `ZERO_RESULTS` | Places API returns nothing, including after progressive token-stripping degradation (strip `flat`/`floor`/`wing`/`room`, retry with `[Building] + [Sub-locality] + [Pincode]`) | → HILT, `geocode_error = 'ZERO_RESULTS'` |
| Multi-candidate | More than one candidate remains after discarding out-of-bounds results (outside the delivery PIN/polygon) | → HILT, `geocode_status = 'NEEDS_HILT'`, candidates `(lat, lon, formatted_address, place_id)` retained for the reviewer |

**Blast radius:** `app/services/geocoding.py` (candidate/bounds logic), `app/services/address.py` (token-stripping degradation), `app/schemas.py` (candidate list field), BQ/Firestore (new `geocode_status` value `NEEDS_HILT`, no new columns). `app/services/sorting.py`'s `usable_pending` filter (currently `sorting.py:49-52`, checks only lat/lon/geohash presence) must also exclude `geocode_status == 'NEEDS_HILT'`, so `tsp.py` never receives an unverified point. `tsp.py` itself: unchanged.

### 5.2 Solitary-outlier trap

Before `compute_groups_and_sequence` (`app/services/sorting.py:19`) commits a DRS, compute each pending stop's distance to its nearest neighbor (or cluster centroid) using the existing `haversine_distance`. This is **tiered, not a single cutoff** — severity scales with distance, and all three numbers are config (§5.6), not hardcoded:

| Tier | Default threshold | Effect |
|---|---|---|
| Suggestion | ≥ 2km | Stop is flagged to HILT as a non-blocking suggestion. DRS creation proceeds normally. |
| Medium intervention | ≥ 5km | Stop is flagged to HILT as requiring review. DRS creation still proceeds (does **not** block), but the flag is elevated — intended to surface to a dispatcher, not just log. |
| Blocked | ≥ 10km | DRS creation is refused for that stop until it's resolved or explicitly overridden by a dispatcher. |

A stop only ever falls into the highest tier its distance qualifies for (10km ⇒ blocked, not also "medium" and "suggestion"). The three thresholds are independent config values, not derived from each other, so they can be tuned without a code change (§5.6).

**Blast radius:** new pre-check function, likely in `app/services/sorting.py` ahead of `solve_route_order`; reuses `tsp.py:17` haversine, adds no new distance math. `write_group_assignments` (`bigquery.py:199`) is skipped only for stops in the Blocked tier, not Suggestion/Medium.

### 5.3 Master-waypoint tier

New module (e.g. `app/db/master_waypoint.py`, mirroring `geocache.py`'s structure) + new Firestore collection (e.g. `master_waypoints`): alias → verified lat/lon, `verified: bool`, `confirmation_count: int`. Checked first in `_geocode()` (`save.py:76`), ahead of the existing `get_cached_geocode_with_outcome` call. A `verified: True` entry is immutable — no code path except the promotion rule below may overwrite it.

**Promotion rule:** an EOD confirmation (§5.4) that corrects a point increments `confirmation_count` for that alias; on the **3rd distinct confirmation** of the same corrected coordinate, it's promoted/updated. This is the one sanctioned exception to immutability.

**Flow — resolution waterfall (where master-waypoint sits):**

```
Incoming consignment address (save_consignments_pipeline, save.py:131)
  │
  ▼
① Master-waypoint lookup   — NEW, app/db/master_waypoint.py
   normalize alias → exact match against `master_waypoints` (verified=True only)
  │
  ├─ HIT ──────────────────────► geocode_status="success", source="master_waypoint",
  │                               $0 cost, no API call. STOP.
  └─ MISS
     │
     ▼
② geocache.py exact/fuzzy lookup   — EXISTING, unchanged (get_cached_geocode_with_outcome)
     │
     ├─ exact_hit / fuzzy_hit (≥85) ─► return cached result. STOP.
     └─ MISS
        │
        ▼
③ BQML vector search (§5.5)   — EVALUATION ONLY, not production yet
   bounded to pincode / geohash-6 partition, cosine similarity via VECTOR_SEARCH
        │
        ├─ above threshold ─► return matched result. STOP.  [gated behind eval sign-off]
        └─ MISS
           │
           ▼
④ Google Places API v1 text search   — EXISTING, geocoding.py (now bounds/multi-candidate aware, §5.1)
           │
           ├─ exactly 1 in-bounds candidate ─► success, save_to_cache(). STOP.
           ├─ 0 candidates (after progressive
           │   token-stripping degradation)   ─► HILT, geocode_error='ZERO_RESULTS'
           └─ >1 in-bounds candidates         ─► HILT, geocode_status='NEEDS_HILT',
                                                   candidates retained for reviewer
```

**Flow — promotion loop (EOD feedback → master-waypoint, the one path allowed to write a verified anchor):**

```
EOD debrief (external mobile app)
  │  driver answers ">500m confirmance question" with reasonCode='A' (or 'D')
  │  + correctedLatitude/correctedLongitude, if captured
  ▼
POST /eod-delivery-feedback (§5.4)  →  app/services/eod_feedback.py
  │
  ▼
master_waypoint.record_confirmation(alias, corrected_lat, corrected_lon)
  │
  ├─ confirmation_count < 3           ─► stored as a pending correction only;
  │                                       live anchor (if any) is untouched
  └─ 3rd DISTINCT confirmation of the
     same corrected coordinate         ─► promote/overwrite `verified` anchor
                                           (reasonCode='D' skips the count and
                                            quarantines immediately instead — §5.1/§5.4)
```

### 5.4 EOD ingestion contract (technical spec — this repo's side only)

This repo does not own the mobile app or the EOD process. This section specifies (a) what change to *recommend* to that system's owners, and (b) the concrete contract this repo will expose to receive the result. Nothing here implies write access to the mobile app's codebase.

**Recommended change to the EOD/mobile system:**
When the EOD debrief's existing >500m confirmance question gets a "not accurate" answer, capture a reason code and, where available, a corrected pin — in addition to whatever it already does for undelivered-rollover.

| Code | Meaning | This repo's resulting action |
|---|---|---|
| `A` | At door/gate — waypoint was inaccurate | HILT review queue; corrected coordinate counts toward §5.3's 3-confirmation promotion |
| `B` | Customer met driver elsewhere (ad-hoc handover) | No coordinate change; stored as a note only |
| `C` | Marked delivered later / app sync lag | No coordinate change; flagged for driver-telemetry sync-lag analysis (out of this repo's scope beyond storing the flag) |
| `D` | Map pin completely wrong | Immediate HILT quarantine, does not wait for 3 confirmations |
| *(omitted)* | App sent no feedback | Stored as `NOT_PROVIDED`; **must never block** the undelivered-rollover/completion write |

**New endpoint on this repo's side** (mirrors the existing `save-consignments`/`run-sorting` router pattern — flat Pydantic request model in `app/schemas.py`, `{"status": ...}` JSON response, errors as `JSONResponse(status_code=..., content={"status": "error", "message": ...})`):

```
POST /eod-delivery-feedback
```

Request body (new `EodDeliveryFeedbackRequest` in `app/schemas.py`):

| Field | Type | Notes |
|---|---|---|
| `drsNo` | string | required |
| `consignmentId` | string | required |
| `actualLatitude` | float \| null | the driver's completion GPS, if captured |
| `actualLongitude` | float \| null | |
| `deliveryOutcome` | string | e.g. `DELIVERED`, `UNDELIVERED_RETRY_NEXT_DAY` — whatever the EOD app already tracks |
| `reasonCode` | `"A" \| "B" \| "C" \| "D" \| null` | null/omitted → stored as `NOT_PROVIDED` |
| `correctedLatitude` / `correctedLongitude` | float \| null | only meaningful with `reasonCode = "A"` or `"D"` |
| `eventTimestamp` | ISO8601 string | when the debrief event happened on the driver's device |

Processing (new function, e.g. `app/services/eod_feedback.py`, called from a new `app/routers/eod_feedback.py` registered in `app/routers/__init__.py`):

1. Look up the consignment's planned lat/lon (already in `consignments_routing`).
2. If `actualLatitude`/`actualLongitude` present, compute delta via the existing `haversine_distance`. If `> 500m` and no `reasonCode` was supplied, record `NOT_PROVIDED` — do not block.
3. Route by `reasonCode` per the table above.
4. Write an audit record scoped to `(consignmentId, drsNo)` — e.g. a new BigQuery table `delivery_audit` (`consignmentId`, `drsNo`, planned lat/lon, actual lat/lon, delta metres, `reasonCode`, `eventTimestamp`).
5. Undelivered-rollover handling (marking for next day) proceeds regardless of whether feedback was supplied — feedback is additive, never a gate on the existing rollover behavior.

**Blast radius:** new router + service module + schema + BQ table. Zero changes to `save.py`/`sorting.py`/`tsp.py` — this is a new, independent ingestion path that only *feeds* §5.3's promotion rule and §5.5's training data.

### 5.5 BQML / vector-search embeddings evaluation

- `ML.GENERATE_EMBEDDING` with `text-embedding-005`, `task_type = 'SEMANTIC_SIMILARITY'`, called through a BQML remote model over a Vertex AI connection (see §2 for references).
- **Hard constraint, unchanged from the original ask:** never search unconstrained. Every `VECTOR_SEARCH`/`ML.DISTANCE` call is pre-scoped to a postal code or geohash-6 partition, and only runs after both the master-waypoint tier (§5.3) and `geocache.py`'s exact/fuzzy lookup have missed.
- **Training/eval data:** EOD-confirmed corrections (§5.4) become labeled ground truth — this is the legitimate use of historical ("post facto") data the repo owner asked for: not retrospective reporting, but a training signal that improves future matching before it's needed again.
- This is an **evaluation phase**, not a committed production path: deliverable is a BQML pipeline + an offline precision/recall report, gating a later decision to wire it into the live save-consignments flow.

**Blast radius:** new BQ dataset/table for embeddings, a BQML remote model resource, a Vertex AI connection (GCP infra, provisioned outside application code), and an offline evaluation script outside `app/`. No production code path calls `ML.GENERATE_EMBEDDING` in this phase.

### 5.6 Configuration & feature flags

This repo is a live prod API (Cloud Run, two endpoints in active use today). Every requirement in §5.1–§5.5 is new behavior being added to that live request path, so this section is itself a requirement, not tooling on the side: **nothing above ships without a flag.**

**Two-layer config, matching the pattern the repo already has:**

| Layer | Where it lives | What goes here | Change requires a redeploy? |
|---|---|---|---|
| Static | `app/config.py`, env vars (existing pattern, `os.environ[...]`) | Project IDs, table names, API keys — things that don't change at runtime | Yes |
| Dynamic | New Firestore collection, e.g. `app_config` | Feature on/off flags, the outlier-tier thresholds (§5.2), the fuzzy/similarity cutoffs, rollout scope | **No** |

The dynamic layer is read through a cached-snapshot accessor that mirrors `geocache.py`'s existing `_verified_entries()` pattern (`app/db/geocache.py:156`, TTL-based process-local cache) — same idiom, new collection. This is why Firestore over env vars for anything behavioral: an env var change needs a new Cloud Run revision; a Firestore doc write is live within one TTL window, which is what canary actually needs.

**Every new flag defaults OFF.** New code merges to `main`/prod disabled — "unimplemented" from the caller's perspective — and is enabled deliberately per §5.6's rollout mechanism below, never by the act of merging.

**Rollout/canary scope is a business dimension, not raw traffic %.** Cloud Run's native revision traffic-splitting exists and is a fine complementary tool, but blast radius here is about *which DRSs/depots* run the new logic, not which raw HTTP requests do. The flag document carries a `rollout` field: either an explicit allowlist (`drsNo`/depot values) for deliberate early testing, or a `rollout_percent` applied via a deterministic hash of `drsNo` — so a given DRS gets consistent behavior for its whole run, and rollout state is describable in plain terms ("depot X is on the new outlier check") rather than statistically.

**The outlier trap's own tiers (§5.2) are a canary mechanism, not just a UX choice.** Suggestion (2km) and Medium (5km) never block anything — only the 10km Blocked tier can refuse a DRS. A sensible rollout is: ship with only Suggestion active (nothing blocks), watch HILT queue volume, then enable Medium, then Blocked — using the same flag-driven per-tier enablement, not a separate mechanism.

**Backfill / "run for past too":** the outlier check and the ambiguity classification (§5.1, §5.2) are pure functions over stored lat/lon and API responses — they don't depend on request-time state. That means the same functions run identically from a standalone backfill script (reading existing `consignments_routing` rows, applying a chosen config snapshot) as from the live pipeline. A backfill run should record which config values it used (see versioning below) so results are reproducible and auditable, not silent.

**Config versioning (for audit/rollback, not a URL version):** each write to the `app_config` document carries an incrementing `version` field (the same optimistic-concurrency idea already available via Firestore). Every BQ/Firestore record this spec adds that resulted from a flagged decision (a HILT entry, an outlier flag, a master-waypoint promotion) stores the config `version` active at the time — so "why did this DRS get blocked" is answerable by looking up that version's threshold values, not guessing from current config. This is the versioning mechanism that matters here — a new REST API version (`/v2/...`) is **not** recommended, since every change in this spec is additive to existing request/response shapes; the one real contract obligation is that consumers of `geocode_status` treat unknown values (like `NEEDS_HILT`) defensively rather than erroring.

**Deliverable:** a `docs/CONFIG.md` (or `.specify/config.md`) documenting every flag/threshold — name, default, effect, which requirement it gates, and rollout state — kept current as flags are added; this is the "config with doc explaining config" this section exists to satisfy.

**Blast radius:** new Firestore `app_config` collection, new cached-accessor module (e.g. `app/config_dynamic.py` or extending `app/db/`), a config-versioning field threaded through every new write in §5.1–§5.4, and a new doc file. No change to existing static `config.py` values or any existing request/response shape.
